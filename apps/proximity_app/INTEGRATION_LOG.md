
## Isolate crash fix

Native SIGABRT on the marking-time face check (temp.log 2026-09-10, Samsung A52s, `flutter run` session): still capture succeeds, the verification worker runs ML Kit face detection in a background isolate (0 faces found, 290ms), then the engine aborts — `[FATAL:flutter/lib/ui/window/platform_message_response_dart_port.cc(53)] Check failed: did_send` → `SIGABRT`, uncatchable in Dart. temp.log kept on disk (user's file, not deleted).

### Trace → root cause (verified, not assumed)

- temp.log lines 39–120: `[ISOLATE] Starting verification worker…` → `BackgroundIsolateBinaryMessenger initialized` → ML Kit model loads → `detectFacesImageByteBuffer` ×2 → `[ISOLATE] ✅ Face detection WORKS in isolate! Detected 0 faces in 290ms` → immediate `FATAL … Check failed: did_send` → `Fatal signal 6 (SIGABRT)`.
- Backtrace frames 24→12 pin the reply path, innermost-first: `com.google_mlkit_face_detection.FaceDetector.onMethodCall` → `MethodChannel$IncomingMethodCallHandler$1.success` → `DartMessenger$Reply.reply` → `FlutterJNI.invokePlatformMessageResponseCallback` → native `did_send` check. Detection itself SUCCEEDED (0 faces logged); the MethodChannel success reply on the background isolate's consumed/invalid response handle killed the process.
- Plugin source (`face_verification 0.3.9`, pub-cache `lib/face_verification.dart` + `lib/src/services/isolate_verification_worker.dart`): `verifyFromImagePathIsolate` runs `compute(isolateVerificationWorker)`, which calls `BackgroundIsolateBinaryMessenger.ensureInitialized` then `detector.processImage` — exactly the log's `[ISOLATE]` lines (string-identical). The Dart-side `try/catch` in that method only maps failures to `null`; NOTHING in Dart can catch the native `did_send` abort. Our code reached it via one call site: `face_verifier_plugin.dart` `verify()` → `_plugin.verifyFromImagePathIsolate(...)`. `MlkitPoseGate` never used an isolate (main-isolate `processImage` already) — no pose change needed beyond hardening.
- Root-cause class confirmed: ML Kit MethodChannel reply redeemed from a background isolate. Fix direction per trace: eliminate the background-isolate call pattern entirely (main-isolate detection measured ~290ms in the same log; existing busy UI covers it; no new user-visible step).

### Fix (semantics frozen: fail-closed, inconclusive-vs-mismatch, 0.70)

- `lib/features/face_identity/face_verifier_plugin.dart` (only behavioral change): `verify()` now calls the plugin's supported main-isolate `verifyFromImagePath` — the isolate variant is never referenced in code again (grep proves elimination; only ban-comments mention it). Exactly ONE plugin call per verify, no retry loop (a second in-flight reply for the same handle is the same crash class — single-invocation is load-bearing). Defense in depth: `verifyTimeout` (10s) + `initTimeout` (30s); timeout → rescan-safe `StateError`; ANY infrastructure throw → rescan-safe `StateError`. The driver already maps every such throw to `inconclusive` (rescan path, burns nothing) — so: never a crash, never a hang, never a mis-mark. Frozen mapping untouched: readable `null`/wrong-id → mismatch (burns 1), match carries the 0.70 boundary score, threshold forwarded verbatim (default `kFaceThreshold`).
- `lib/features/face_identity/pose_gate_mlkit.dart`: detection was already main-isolate; hardened without behavior change — `detectTimeout` (10s) → fail-closed `null` (silent wasted beat, loop never stalls), injectable `FaceDetector` test seam, and a MAIN-ISOLATE-ONLY contract comment (never `compute`/`Isolate.spawn`, never cross isolates).
- `lib/features/face_identity/face_verifier.dart`: header comments only (isolate variant documented as banned, main-isolate + timeout contract). No code change.
- Plugin pin (rule 3): NO upgrade. Verified live via pub.dev API on 2026-09-10: `face_verification` latest = 0.3.9 (published 2026-09-06; changelog is toolchain/AGP/`image`-RangeError chores — no reply/isolation fix) and `google_mlkit_face_detection` latest = 0.15.1 (changelogs 0.13.2→0.15.1 are native-SDK bumps + Kotlin/Swift migration + build changes — no reply/isolation fix). Pins `face_verification ^0.3.9` / `google_mlkit_face_detection ^0.15.1` unchanged; pubspec untouched.
- Ownership: `features/face_identity/*` (2 impl files + header comments) + new test file only. Untouched: setup/mark/live/records/account/shells/routes/tokens/drivers/claim, `temp.log`, pubspec.

## Desktop select + live inbox

Two tester-verified defects, presentation/navigation only. Frozen kept: decision paths, draft/snapshot semantics, approve/reject copy (`Approve N`/`Reject N` labels verbatim), proof-pipeline timings (reused existing 2s cadence — no new timing), thresholds, network (reads are local driver state only). No Checkbox widgets added anywhere (grep-verified in all touched files); the session-edit per-round correction boxes (the one sanctioned exception) untouched.

### Root causes (verified, not assumed)

- FIX 1 — desktop mouse selection: `StudentCard` wired ONLY `onTap`/`onLongPressStart` — no `onSecondaryTap`, no per-list mode toggle existed anywhere. Long-press is undiscoverable/impossible-feeling with a mouse; plain left-clicks already toggled while selecting (`_handleTap` — verified, kept verbatim).
- FIX 2 — inbox live updates: `HostDriver` is a plain `Provider` over mutating server state — it never notifies. So `ManualInboxView` (pure function of the `pending` prop) re-rendered only when callers rebuilt: the focused `LiveInboxScreen` (`ConsumerWidget` watching the never-changing provider instance) builds exactly once, and the take host while idle rebuilds its 2s `_idlePoll` ONLY on waiting-room deltas (`_logWaitingDelta`), never manual deltas — arrivals while idle never appeared, and the `Inbox (N)` badge went stale too. While live, the 1s elapsed tick incidentally rebuilt every second, which is why the bug read as idle/focused-only.
