10 · Flutter + Dart 🐦

One codebase, every screen

What it does

Compiles one UI + logic to Android, iOS, macOS, Windows, Linux, Web.

Why this one

Small team can't maintain native apps; attendance logic must be identical.

Good ↔ Trade-off

Same protocol + fast UI + one test suite ↔ shims for BLE/camera, larger size.

Prevents

Logic drift ("Android marks, iOS doesn't"); desktop/web fail closed, never weakly mark.

Speaker notes

Flutter and Dart compile one codebase to Android, iOS, macOS, Windows, Linux and Web, so a small team maintains one attendance protocol instead of three native apps. Pure logic lives in testable monorepo packages with 1400+ fast unit tests, and desktop and web builds fail closed — they cannot mark, instead of marking weakly. The cost is platform shims for BLE, camera and file saving, a larger binary, and quirks like Apple stripping BLE payload data leaking through.

11 · Firebase Auth + Firestore 🔥

Identity once. Records always.

What it does

Google sign-in for identity; NoSQL store + rules + indexes for records.

Why this one

No passwords, no server to run; org falls out of the email domain.

Good ↔ Trade-off

Free tier, transactions, offline sync ↔ Google-dependent, no custom server logic.

Prevents

Fake typed names; double-enrollment races; cross-org snooping; silent data loss.

Speaker notes

Google sign-in supplies a verified email and user ID with the institute derived from the email domain — no passwords, no custom user store. Firestore holds users, device bindings and sessions behind server-enforced rules plus composite indexes, and its transaction resolves simultaneous one-device claims to exactly one winner. Sync is offline-first with union-merge, tombstone deletes and idempotent replay; the free-tier trade-off is no custom server logic and no server-side certificate re-check.

11 / FirebaseServerless · org-scoped · union-merge

12 · Version floor ⏫

Old builds retire on schedule

What / Why

Cloud doc app_config/min_version declares the minimum safe build; older apps see a blocking update screen. No extra SDK.

Trade-off / Prevents

Disk-cached so it enforces offline — but a build that never goes online can't learn the new floor. Kills downgrade attacks and cryptic bad-signature errors.

Speaker notes

When crypto, face, or rules change, the floor retires unsafe builds so attackers can't pin an old APK to bypass new gates. The cached floor enforces across restarts even offline.

14 · BLE + mesh relay 📡

Range is the sensor

What it does

Professor shouts a rotating secret; front rows re-shout so back rows hear.

Why this one

BLE travels ~10–30 m. Campus Wi-Fi is routed across buildings and proves nothing.

Good ↔ Trade-off

One plugin, no hardware, 500-seat halls via relay ↔ Apple strips payloads; needs foreground + Bluetooth on.

Prevents

Hostel / VPN proxy — forwarded screenshots are already stale; fixes back-row dead zones.

Speaker notes

Bluetooth Low Energy is the proximity sensor: the professor shouts a fresh 8-byte secret every 10 seconds and front-row phones re-shout it under TTL, jitter, dedup and split-horizon rules so back rows in 500-seat halls hear it. Campus Wi-Fi is routed across buildings so it can never prove the room — only short-range radio can. Apple stacks strip attached payloads so Apple hosts alternate challenge and hint packets, radio needs foreground plus Bluetooth on, and thresholds need per-hall tuning.

15 · HTTPS + discovery 🔒

BLE has range. Wi-Fi has bandwidth.

What it does

Professor runs a per-class HTTPS server; UDP beacons + BLE hint + typed IP help students find it.

Why this one

BLE can't carry bulk proofs; Wi-Fi can't prove locality. Each does what it's good at.

Good ↔ Trade-off

No internet, standard TLS, rate limits ↔ some APs block broadcasts; falls back to hint + typed IP.

Prevents

Evil-twin relays via channel binding; replay floods; rogue professors — students verify before signing.

Speaker notes

The professor runs a tiny per-class HTTPS server on the LAN while UDP beacons, a BLE IP-hint and a typed-IP fallback help students find it — no internet needed. A per-session certificate plus TLS channel binding ties the encrypted pipe to the signature, rate limits tame lecture-herd floods, and single-use IDs stop replay floods. Before signing anything the student verifies the professor signature and key pin, which defeats rogue-professor harvesting and evil-twin relays.

16 · Ed25519 + HMAC + SHA-256 ✍️

Small, fast, unforgiving signatures

Ed25519 · signs

Students sign proofs, professors sign challenges + receipts. 1000–2500 verifies per lecture is trivial.

HMAC-SHA256 · rotates

Derives 10-second challenges and per-student tokens; 8 bytes on air; single-use + freshness wrapped.

SHA-256 · binds

Fingerprints keys, binds tickets, opaque face IDs. Fingerprint only — not encryption.

Prevents

Forged proofs, pre-play, replay, linkability across lectures, ticket transplant.

Speaker notes

Ed25519 signs every student proof, professor challenge and receipt with small fast signatures — thousands of verifies per lecture are trivial. HMAC-SHA256 derives the 10-second challenge, per-student response token and rotating radio alias from window secrets, so future tokens can never be pre-played and lectures stay unlinkable. SHA-256 fingerprints keys, binds face and liveness tickets into signatures, and hashes Gmail into opaque face IDs; freshness of 17 seconds plus single-use window IDs and a dedup cache kills replay.

16 / Crypto trioCompact · deterministic · single-use

17 · Hardware keys + X.509 offline verify 🔑

A file copy is useless without the silicon

What it does

Signing key sealed by a non-exportable P-256 device key in StrongBox / TEE / Secure Enclave; AES-GCM wraps it.

Why this one

Software keys travel with their files. Chip keys never leave the phone.

Good ↔ Trade-off

FULL / STD tiers, offline-verifiable ↔ needs modern hardware; no server re-check on free tier.

Prevents

Lent-phone marking, cloned-app fraud, tier lies — bad chains land on manual, never auto-present.

Speaker notes

The attendance signing key is sealed by a non-exportable P-256 device key inside StrongBox, the TEE or the Secure Enclave, wrapped with AES-GCM — a file copy without the silicon unwraps to nothing. Every proof carries a fresh hardware signature over the live challenge, and the professor's phone verifies the X.509 chain against pinned Google and Apple roots fully offline. Bad chains land on the manual path as device-unproven, never auto-present; software test keys can never confirm.

18 · FaceNet + ML Kit · MiniFASNetV2 liveness 👁️

The key proves the phone. Face proves the holder.

What it does

5-angle on-device enrollment; ~1-sec verify stamps a 5-minute signing ticket. Gallery never leaves the phone.

Why this one

One maintained plugin replaced vendored custom models; fully offline with bundled model.

Good ↔ Trade-off

Fast, version-pinned ↔ needs good light; twins flag each other for one-tap resolve.

Prevents

Lent-phone proxy; photo / screen replay via vitality + blink/smile gates; face never reaches the cloud.

Speaker notes

FaceNet plus ML Kit enrolls five angles on-device and verifies in about a second, stamping a 5-minute ticket that unlocks signing — the gallery never leaves the phone and model bumps force re-enrollment rather than cross-version matching. MiniFASNetV2 adds a passive vitality score plus a shuffled blink-or-smile walk at enroll, graded onto the signed ticket, so a photo must beat vitality, face, ticket and radio gates together. Near-miss liveness gets a free rescan, mismatches burn attempts into a needs-review queue, twins are one-tap resolved, and duplicate faces across Gmails are flagged in professor-phone RAM only, wiped at close — the cloud carries just PRESENT, ABSENT or FLAGGED.

20 · Live threat demo

Five attacks. Five honest failures.

No BLE secret in range → No signal. Nothing to sign, nothing sent.

🤝 Lent phone

Face mismatch → no ticket → key won't unseal. Needs review.

🐒 Cloned app

Copy without silicon unwraps to nothing. Integrity gate refuses first.

🎣 Fake professor

Bad signature + key pin → student signs nothing. Harvest fails.

🔁 Replay

Stale 10-sec token, single-use ID → rejected + deduped.

Speaker notes

Each attack lands on an honest verdict or the manual path, never a fake success. Hostel joins hear nothing; lent phones fail face; clones lack the chip; fake professors fail signature checks before any signing; replays are stale and single-use.

21 · Honest limits

What Proximity deliberately doesn't do

🚫 No background marking

Foreground-only on every OS — background promises would be lies the OS won't keep.

🚫 No server re-check (yet)

Free-tier constraint; professor verifies hardware chains offline.

🚫 No institute PKI yet

Professor roles are self-asserted; directory reads are advisory; no self-service reset shortcut.

🚫 No UWB distance-bounding · zero biometrics in cloud

Colluding-relay wormhole remains theoretical; face vectors live in phone RAM only, cloud carries PRESENT / ABSENT / FLAGGED.

Speaker notes

A live relay plus a live victim face across two full windows could theoretically wormhole within ten seconds — at the cost of a dedicated accomplice for the whole lecture, far above casual proxy. Biometrics never leave devices.
